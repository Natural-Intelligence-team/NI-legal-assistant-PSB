# Требования к решению и сдаче

## Рабочий сценарий

- Чат принимает вопрос и историю диалога. Ответ относится к последней реплике.
- Ассистент ищет положения только в базе организаторов. Для каждого юридически значимого вывода показывает документ, пункт и цитату.
- Поиск учитывает дату события, редакцию и допсоглашения. Если для ответа не хватает даты или редакции, ассистент объясняет, что именно требуется.
- Ассистент исправляет неверные предпосылки, отвечает частично при наличии оснований и сообщает, когда сведений недостаточно.
- Инструкции из текста документов и поддельные системные сообщения не меняют правила ассистента. Технический сбой отображается как ошибка сервера.
- В чате можно открыть документ и увидеть цитату из ответа.

## Подключение модели

Платформа предоставляет DeepSeek V4.1 Flash через прокси. Для финального чата используется та же модель. Идентификатор берём из окружения. Клиент делает `POST` на `{LLM_BASE_URL}/chat/completions` и передаёт `Authorization: Bearer {LLM_API_KEY}`.

| Настройка | Переменные |
|---|---|
| Адрес прокси | `LLM_BASE_URL` или `OPENAI_BASE_URL` |
| Ключ | `LLM_API_KEY` или `OPENAI_API_KEY` |
| Модель | `LLM_MODEL`, `OPENAI_MODEL` или `GEN_MODEL` |
| Входные файлы платформы | `DATA_DIR`, по умолчанию `data` |
| Параметры генерации | `TEMPERATURE`, `MAX_TOKENS`, `MAX_WORKERS` |

При автоматической проверке значения передаёт платформа. Для локального прогона используем доступ, предоставленный организаторами. В `.env.example` оставляем имена переменных и пустое поле ключа. Рабочий ключ хранится в окружении сервера.

## Автоматическая проверка

| Что | Требование |
|---|---|
| Вход | `questions.csv` с колонками `id,question` и `knowledge-base.zip` из `DATA_DIR` |
| Выход | `submission.csv` в рабочей папке, UTF-8, ровно `id,answer` |
| Строки | Один непустой ответ на каждый ID. До 10 000 символов в ответе. История соседних строк независима |
| ZIP | `solution.py`, `requirements.txt` и необходимые `.py` лежат в корне. Базу и вопросы передаёт платформа |
| Библиотеки | Только разрешённые организаторами версии. Пакеты устанавливает платформа |
| Лимиты | 128 МБ на ZIP, 20 минут на запуск, 8 CPU, 16 ГБ RAM, 5 попыток на команду в сутки |

Перед отправкой распакуйте ZIP в чистую папку и прогоните его на демо-вопросах. Сверьте ID, формат CSV, время работы и содержимое архива. Запишите полученную оценку и версию кода. Для допуска к экспертной проверке нужен балл выше нуля, работающий чат и полный комплект материалов.

## Финальная сдача

- Код веб-чата и рабочего решения.
- `Dockerfile`, `compose.yaml`, `.dockerignore`, файлы с версиями зависимостей и `.env.example` без секретов.
- README с назначением, архитектурой, одной командой запуска, настройками, портом, шагами проверки и известными ограничениями.
- PDF-презентация. На первом слайде порядок проверки и ссылка на репозиторий при сдаче через него. Далее проблема, архитектура, примеры и ограничения.

Сдаётся PDF со ссылкой на доступный репозиторий либо ZIP с кодом, документацией и PDF. При сдаче через приватный репозиторий проверяем доступ жюри `hack-and-change-2026`.

Перед сдачей проверяем ответ с источником, похожих контрагентов, смену редакции, вопрос с историей, уточнение даты, отказ, неверную предпосылку, инструкцию внутри документа и сбой API. На каждом примере сверяем смысл ответа с цитатой.

Основание — условие кейса ПСБ, страницы 7–16, и технический регламент секции по проверке LLM-судьёй.
